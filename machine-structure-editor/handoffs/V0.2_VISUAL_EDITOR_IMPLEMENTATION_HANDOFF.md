# 2. Core architecture

The central architectural principle remains:

> The physical machine is the machine. Firmware is a versioned implementation of that machine, not the machine's identity.

Canonical direction:

```text
Physical Machine
        ↓
Canonical Machine Model
        ↓
Firmware Requirements / Mapping
        ↓
Target Firmware + Version
        ↓
Generated Configuration / Representation
```

Reverse direction:

```text
Firmware / Configuration
        ↓
Semantic Interpretation
        ↓
Canonical Machine Model
```

The canonical model is the authoritative semantic representation.

The visual editor is an authoring, inspection, and presentation layer over that canonical model. It is not a second independent semantic model.

# 4. Important architectural boundaries

## Canonical semantic model

The canonical semantic model owns machine meaning.

Important classes include:

- `Machine`
- `MachineComponent`
- `HardwareDefinition`
- `SemanticPort`
- `Function`
- `Capability`
- `Controller`
- `ControllerResource`
- `ControllerResourceAssignment`
- semantic connections
- semantic relationships

The canonical model is the authoritative source for these meanings.

## Visual model

The visual model owns editor presentation state such as:

- node position
- node size
- rotation
- visual ports
- visual connections
- grouping
- views
- pan
- zoom

Visual state may refer back to canonical semantic objects, but should not become a duplicate semantic authority.

## ModelStore

`ModelStore` owns persistent editor state and edit history.

It provides:

- atomic commits
- undo
- redo
- save
- load
- new document
- modified-state tracking
- listeners

Semantic mutations are intended to pass through this layer when used by the application.

# 9. Visual graphics behavior

The graphics layer now supports semantic port editing without confusing it with connection interaction.

Current behavior:

- single click / drag on a port remains connection interaction
- double-click on a port opens semantic port editing
- node movement remains independent
- visual port updates can mirror semantic port changes
- canvas scene synchronization rebuilds/updates graphics from the visual model

This distinction is important:

```text
single click / drag
    → connection interaction

double click
    → semantic port authoring
```

The same principle should be preserved for future interactive elements.

# 12. Important implementation principles for the next chat

## Do not reconstruct large existing files from memory

A previous failure involved accidentally replacing a large semantic-model file with an incomplete reconstruction.

Avoid that.

When modifying an existing substantial file:

1. inspect the exact current version
2. preserve existing content
3. make the smallest necessary change
4. test
5. keep the replacement complete when giving instructions to the user

## Prefer focused modules

Repeated friction is architectural evidence.

If a module becomes large because it owns one genuinely cohesive responsibility, that can be acceptable.

Do not split code merely to make line counts look small.

Do split when responsibilities are genuinely distinct.

## Do not prematurely move research decisions into implementation

A promising idea is a candidate until the research/architecture side settles it.

The implementation can support a candidate without silently making it canonical.

# 13. Hardware catalog boundary

Online/downloadable hardware catalogs are deliberately not being forced into V0.2 yet.

The architecture already has the correct distinction:

```text
Online Catalog
      ↓
Adapter / Importer
      ↓
Normalized HardwareDefinition
      ↓
MachineComponent
      ↓
Canonical Machine
```

`HardwareDefinition` is distinct from a physical `MachineComponent`.

Do not collapse those concepts merely because a catalog UI becomes desirable.

# 18. Immediate next likely direction

The controller/resource semantic layer is now sufficiently mature that the next useful work should probably be visual-editor integration rather than more isolated CRUD layers.

The next chat should decide how canonical controller resources become visible/selectable in the editor.

Questions worth resolving in that phase:

- Should controller resources appear as nodes?
- Should they be represented as controller sub-elements?
- How should a resource be selected without creating a second semantic representation?
- How should assignments be displayed visually?
- Should assignment be made from a source component/port to a controller resource?
- How should machine/controller/resource hierarchy appear at different zoom levels?
- What belongs in the canvas versus a details/properties panel?
- How should semantic resource ownership be distinguished from physical wiring?
- How should visual filtering expose controller resources without changing the machine?

Do not automatically implement one of these choices before establishing the UI/semantic boundary.
