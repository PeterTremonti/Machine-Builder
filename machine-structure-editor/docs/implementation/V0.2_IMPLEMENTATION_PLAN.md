# Machine Structure Editor — V0.2 Implementation Plan

## Status

**Version:** V0.2

**Status:** Initial planning

**Previous milestone:** `v0.1.0`

**Related research milestone:** O0.1 / Research V0.1

---

# 1. V0.2 Purpose

V0.1 established the visual interaction foundation of the Machine Structure Editor.

V0.2 changes the purpose of the editor from primarily demonstrating visual structure and connection mechanics to becoming the first **semantic authoring environment** for Machine Builder.

The central goal is:

> The editor must be capable of authoring and editing the canonical machine model while maintaining a separate visual representation of that model.

The editor is therefore both:

* a viewer/inspection environment
* an authoring/editing environment

These are modes of interaction with the same underlying machine representation, not separate semantic models.

---

# 2. Core V0.2 Architecture

The intended relationship is:

```text
             ┌──────────────────────────┐
             │ Canonical Machine Model  │
             │                          │
             │ semantic truth / state   │
             └────────────┬─────────────┘
                          ↕
               Semantic / Model Boundary
                          ↕
             ┌────────────┴─────────────┐
             │   Visual Machine Editor  │
             │                          │
             │ author / edit / inspect  │
             │ view / navigate          │
             └──────────────────────────┘
```

The visual editor is not merely a projection of an existing canonical model.

User actions may create or modify canonical semantic information.

The canonical machine model remains the authoritative structured representation once those semantic changes are committed.

---

# 3. V0.2 Primary Goals

V0.2 should concentrate on five closely related goals.

## Goal A — Establish the canonical machine-model foundation

Create the first minimal structured semantic model needed to represent a real machine independently from the visual editor.

## Goal B — Establish the semantic/model boundary

Provide a clean translation between canonical semantic objects and visual objects.

## Goal C — Make the editor a semantic authoring tool

Allow users to construct machine semantics through normal editor actions.

## Goal D — Support incomplete / partially specified machines

A machine should be buildable before every component specification is known.

## Goal E — Establish the beginning of structured persistence

Define an appropriate machine/project data representation.

Persistence should be designed around the canonical model plus visual state rather than simply serializing the current visual editor.

---

# 4. Canonical Model Foundation

V0.2 should create the minimum canonical entities required to prove the architecture.

The initial domain should include concepts such as:

```text
Machine
Machine Component
Subsystem
Port / Interface
Connector
Pin / Terminal
Connection
Controller
Controller Resource
Function
Capability
Property
Calibration
Provenance
Hardware Definition
Catalog Product / Product Version
```

Not every concept must become a complex class hierarchy immediately.

The implementation should begin with the smallest useful representation that preserves the distinctions established by the research work.

---

# 5. Machine Component vs Hardware Definition

A major V0.2 requirement is to keep the **machine-specific component** separate from the **hardware definition/product identity**.

The conceptual relationship is:

```text
Machine Component
       ↓
Hardware Definition
       ↓
Catalog Product / Product Version
```

A Machine Component represents the thing in the machine being built.

A Hardware Definition represents what is known about the physical hardware.

A Catalog Product represents an identifiable product or product version that may supply that definition.

These are related but are not interchangeable.

---

# 6. Part / Component Replacement

V0.2 should establish the architecture needed for a future **Replace Component** operation.

Replacement must not mean:

```text
Delete old component
Create new component
Reconnect everything
```

Instead:

```text
Existing Machine Component
        ↓
preserve component identity
        ↓
replace or enrich hardware definition
        ↓
same Machine Component
        ↓
relationships preserved
```

The following should normally survive replacement:

* machine component identity
* machine role
* physical placement
* subsystem membership
* existing connections
* functions/relationships
* user-authored machine context

unless the user explicitly chooses to change them.

## Replacement sources

The operation should support at least two cases.

### Existing catalog item

The user may decide:

> I want to use an existing catalog item already in the Machine Builder hardware catalog.

The user can therefore replace/associate the component's current hardware definition with an existing catalog product.

### New hardware definition

The user may instead decide:

> This is a different part that is not yet in the catalog.

The user should be able to create or associate a new Hardware Definition and later enrich it with manufacturer, model, specifications, connector information, measurements, etc.

The Machine Component itself remains the same machine object in both cases.

### Replacement Reconciliation:

Replacing a hardware definition does not guarantee that all existing
relationships remain directly compatible.

After replacement, the editor should compare the old and new hardware
definitions and identify:

- preserved relationships
- changed capabilities
- removed resources
- newly available resources
- incompatible existing connections
- connections with no direct equivalent
- ambiguous resource mappings
- potential reassignment candidates
- recommended old-resource → new-resource mappings
- alternative suggested mappings where no direct match exists
- confidence/reason information for those recommendations
- user ability to accept, change, or reject each mapping
- physical connector mismatch flagged separately from semantic/resource compatibility
The editor should not silently discard existing relationships.

Where a direct mapping does not exist, the editor should present a
mismatch/reassignment review and allow the user to reassign an existing
relationship to an appropriate resource on the replacement component.

The replacement process should therefore be understood as:

    Replace definition
        ↓
    Reconcile relationships/resources
        ↓
    Identify mismatches
        ↓
    Offer reassignment
        ↓
    Review changes
        ↓
    Commit

This is particularly important for controllers, where a replacement may
provide different resource names, capabilities, pin counts, electrical
characteristics, or available ports.

---

# 7. Partially Specified Machines

V0.2 must not require every machine field to be known.

A user should be able to construct a machine such as:

```text
Temperature Sensor

Known:
    machine role
    intended placement
    existing connections

Unknown:
    exact manufacturer
    exact model
    exact electrical specifications
    exact dimensions
```

This is a valid machine state.

The software must not require users to invent placeholder specifications merely to satisfy schema requirements.

---

# 8. Information State

The data model should eventually distinguish states such as:

```text
Unknown
Unspecified
Known
Estimated
Inferred
Planned
User-authored
Verified
Not applicable
```

V0.2 does not need to implement every state completely, but the model must not make it impossible to distinguish meaningful states later.

---

# 9. Provenance

Semantic information authored through the editor should be distinguishable from externally sourced information.

Example:

```text
source:
    user

method:
    visual editor authoring

evidence type:
    authored
```

Other future provenance examples include:

```text
manufacturer documentation
manual measurement
photograph
firmware-derived
reverse engineered
calculated
inferred
imported
```

The provenance structure should be designed to support future evidence tracking without requiring all provenance information to be known immediately.

---

# 10. Visual Model Boundary

The V0.1 Visual Model remains useful.

V0.2 should not replace it with the canonical machine model.

Instead:

```text
Canonical Machine Component
        ↕
Semantic / Visual Adapter
        ↕
VisualNode
```

and:

```text
Canonical Port
        ↕
Semantic / Visual Adapter
        ↕
VisualPort
```

and:

```text
Canonical Connection
        ↕
Semantic / Visual Adapter
        ↕
VisualConnection
```

Visual-only information remains visual state.

Examples include:

* canvas position
* node size
* rotation
* routing geometry
* selection
* zoom
* pan
* collapsed/expanded state
* view-specific presentation

The rendered graphics themselves must not become the canonical machine data.

---

# 11. Semantic Authoring

The editor should be able to create semantic machine information.

Examples include:

```text
Create Machine Component
Create Subsystem
Create Port
Create Connection
Assign Function
Assign Capability
Assign Controller Resource
Set Property
Set Calibration
Assign Hardware Definition
```

The exact operation vocabulary may grow as the canonical model develops.

The existing mutation architecture from V0.1 should be extended rather than discarded.

---

# 12. Editing and Viewing Modes

The editor should eventually support two conceptual modes.

## Viewing mode

Primarily for:

* inspection
* navigation
* understanding
* exploring the machine structure

## Editing mode

For:

* creating components
* changing semantic relationships
* changing properties
* replacing hardware definitions
* creating/deleting connections
* modifying machine structure

Both modes operate on the same canonical model.

Viewing mode is not a separate data model.

---

# 13. Change Review

A future change-review system is desirable but is **not a required V0.2 feature**.

The intended direction is:

```text
User operation
      ↓
Pending semantic changes
      ↓
Review / confirmation
      ↓
Commit
```

A review might display:

```text
Added Temperature Sensor

Connected:
    Sensor → Temperature Controller

Assigned role:
    temperature measurement

Hardware definition:
    unspecified
```

The existing mutation system should remain compatible with eventually grouping changes into a reviewable transaction/change set.

---

# 14. Compatibility Architecture

The V0.1 compatibility engine is deliberately provisional.

V0.2 should begin moving compatibility from generic visual-port properties toward canonical semantic information.

Conceptually:

```text
Canonical Port / Interface Semantics
              +
Canonical Connection Constraints
              ↓
      Compatibility Engine
              ↓
       Visual Feedback
```

Compatibility may eventually consider:

* connection domain
* semantic role
* direction
* voltage
* current
* protocol
* interface type
* connector compatibility
* pin/terminal compatibility
* controller-resource availability
* machine-specific constraints

V0.2 should implement only the subset required to demonstrate the architecture.

---

# 15. Physical Connection vs Semantic Relationship

The V0.1 decision remains valid.

A physical connection is not inherently directional:

```text
Port A ↔ Port B
```

A semantic relationship may be directional:

```text
Temperature Sensor
    produces measurement
          ↓
Temperature Controller
    consumes measurement
```

The physical connection and semantic relationship should remain separate concepts.

The visual editor must not infer physical direction merely from the user's drag gesture.

---

# 16. Component and Catalog Relationship

The hardware catalog should not become the canonical machine model.

The intended relationship is:

```text
Catalog
    ↓
Hardware Definition
    ↓
Machine Component
```

A Machine Component may exist without a catalog match.

A catalog item may describe hardware that is not currently used by a machine.

A single catalog definition may potentially support multiple machine components.

This distinction should remain explicit in the architecture.

---

# 17. Structured Storage Direction

V0.2 should establish a structured persistence approach rather than using a spreadsheet as the canonical machine database.

The expected machine/project information includes nested relationships and metadata such as:

* objects
* identifiers
* ports
* connections
* properties
* provenance
* hardware definitions
* catalog references
* semantic relationships
* visual state
* version history

A spreadsheet may remain useful for:

* human review
* imports
* exports
* tabular catalogs
* reporting

but should not become the canonical storage representation of the machine.

The exact persistence technology is a V0.2 architecture decision.

The implementation should not prematurely commit to a storage engine merely because it is familiar.

---

# 18. Persistence Scope

The first persistence milestone should be able to represent at least:

```text
Canonical machine state
        +
Visual editor state
        +
hardware-definition references
        +
provenance where available
```

It should be possible to reopen a saved machine and recover both:

* its semantic structure
* its visual arrangement

without conflating those two layers.

---

# 19. Real Machine Test

V0.2 should move from generic prototype objects toward a simplified real machine.

The first useful test should be a deliberately small machine containing several real relationships.

Potential candidates include the Promega or another already-researched machine.

The purpose is to prove:

```text
real machine concept
        ↓
canonical model
        ↓
visual authoring
        ↓
semantic editing
```

rather than simply proving another generic UI feature.

---

# 20. V0.2 Implementation Sequence

The recommended sequence is:

### Stage A — Canonical model skeleton

Create the minimum semantic model.

### Stage B — Semantic/model boundary

Create the adapter or translation layer between canonical objects and visual objects.

### Stage C — Visual projection

Display canonical machine objects in the existing editor.

### Stage D — Semantic authoring

Make editor actions create/update canonical objects.

### Stage E — Semantic connections

Connect the V0.1 physical connection interaction to canonical connections and semantic relationships.

### Stage F — Component/hardware definition relationship

Allow machine components to exist without an exact hardware definition.

Introduce the architecture required for future component replacement.

### Stage G — Improved compatibility

Begin consuming canonical semantics.

### Stage H — Persistence

Define and implement the first durable structured machine/project representation.

### Stage I — Real machine test

Build and edit a simplified real machine using the new architecture.

---

# 21. What V0.2 Should Not Attempt

V0.2 should not attempt to implement the entire Machine Builder vision.

Explicitly defer:

* full hardware catalog system
* supplier aggregation
* complete firmware generation
* full firmware import
* every ontology entity
* every possible relationship type
* advanced routing
* harness modeling
* wire-length calculations
* 3D connector geometry
* Blender integration
* semantic zoom
* complete accessibility system
* full change-review UI
* automatic machine inference
* complete machine validation
* comprehensive safety engineering
* complete provenance management

These remain future work.

---

# 22. V0.2 Success Criteria

V0.2 should be considered successful if the system can demonstrate:

```text
1. A canonical machine object can exist independently of the UI.

2. The editor can display that canonical object.

3. The editor can create a new machine object.

4. The editor can modify a canonical relationship.

5. The visual representation updates from semantic changes.

6. Semantic changes can update the visual representation.

7. A machine component can exist with incomplete hardware information.

8. A machine component can eventually reference an existing catalog definition
   or a newly created hardware definition without replacing the machine object.

9. Physical connections remain distinct from semantic signal relationships.

10. The resulting machine state can be persisted in a structured representation.
```

A simple machine built entirely through the visual editor should be sufficient to demonstrate the core architecture.

# 23. Testing Strategy

Automated tests should expand to cover:

* canonical model objects
* relationships
* provenance
* unknown/unspecified states
* semantic mutations
* visual-to-semantic synchronization
* semantic-to-visual synchronization
* component definition replacement
* connection relationships
* compatibility

Interactive tests should cover:

* authoring a new machine
* creating components
* editing properties
* creating relationships
* changing hardware definitions
* preserving connections during component-definition replacement
* saving
* reopening
* viewing vs editing behavior

---

# 24. Research / Implementation Boundary

Research remains responsible for:

* ontology definitions
* terminology
* semantic distinctions
* architecture
* standards
* unresolved conceptual questions

Implementation remains responsible for:

* software architecture
* data structures
* UI behavior
* persistence implementation
* tests
* integration

When implementation exposes a semantic problem, send the concrete problem back to research.

When research establishes a concept, document its implementation implications and hand it to the implementation work.

---

# 25. Carry-Forward to V0.3

Possible V0.3 areas will be determined after V0.2 testing.

Likely candidates include:

* richer hardware catalog integration
* advanced component replacement
* change-review UI
* stronger provenance
* richer machine relationships
* more sophisticated compatibility
* subsystem editing
* controller-resource mapping
* firmware representation
* deeper machine validation

These are candidates, not commitments.
