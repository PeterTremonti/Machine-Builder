# Machine Structure Editor — V0.1 Implementation Plan

## Status

**Current phase:** Planning / refactor preparation

**Target:** V0.1 Visual Structure Editor

**Related roadmap:** `IMPLEMENTATION_ROADMAP.md`

---

# 1. Initial Plan

V0.1 establishes the working visual-editor foundation for Machine Builder.

The version should remain intentionally small.

The priority is not to build the complete Machine Builder system. The priority is to prove that the editor can represent, manipulate, and visually connect machine structures in a way that can later support the canonical machine model.

The current working prototype already demonstrates much of this interaction.

The immediate objective is therefore to:

1. Preserve the behavior that is already working.
2. Refactor the oversized `canvas.py`.
3. Add the remaining basic connection interaction.
4. Test the result thoroughly.
5. Document lessons learned for V0.2.

# 4. Architecture Refactor

Before adding more features, split the oversized graphics/editor implementation into smaller modules.

The first refactor should preserve behavior rather than introduce new behavior.

Initial target:

```text
src/
└── machine_builder/
    ├── app.py
    ├── canvas.py
    │
    ├── graphics/
    │   ├── __init__.py
    │   ├── node.py
    │   ├── port.py
    │   ├── connection.py
    │   └── palette.py
    │
    ├── visual_model.py
    ├── mutations.py
    ├── store.py
    └── compatibility.py
```

## Module responsibilities

### `app.py`

Application startup only.

### `canvas.py`

Main editor orchestration.

It coordinates:

* scene
* view
* model store
* editor actions
* model synchronization
* node creation
* node deletion
* connection creation
* connection deletion
* selection
* undo/redo

It should not contain the implementation of every visual object.

### `graphics/node.py`

`NodeGraphicsItem`

Responsible for node presentation and node-local visual behavior.

### `graphics/port.py`

`PortGraphicsItem`

Responsible for:

* port appearance
* persistent labels
* status symbols
* hover state
* connection-start interaction

### `graphics/connection.py`

`ConnectionGraphicsItem`

Responsible for:

* connection rendering
* connection selection appearance
* mouse interaction with the connection itself

### `graphics/palette.py`

`PaletteList`

Responsible for palette presentation and drag behavior.

### Existing model modules

`visual_model.py`, `mutations.py`, `store.py`, and `compatibility.py` remain separate.

# 6. Restore V0.1 Port Presentation

After the structural refactor is verified, restore the tested port presentation:

### Persistent labels

Port labels should remain visible rather than requiring hover.

Labels may appear outside node boundaries when necessary to preserve readability.

The placement strategy may be revisited when nodes become more complex.

### Status symbols

Use both color and a symbol:

```text
✓  compatible
?  unknown / conditional
×  incompatible
```

The symbol should be visible during connection evaluation.

Color must not be the only source of information.

---

# 7. Add Connection Selection and Deletion

After the refactor and port presentation are stable:

1. Make connections selectable.
2. Visually distinguish a selected connection.
3. Allow Delete to remove the selected connection.
4. Use the existing `DeleteConnection` mutation.
5. Verify undo restores the exact connection.
6. Verify redo removes it again.

Connection deletion must not require undoing unrelated previous operations.

---

# 8. Connection Direction Investigation

V0.1 should document the distinction between:

### Physical connection

```text
Port A ↔ Port B
```

### Signal relationship

```text
Sensor → Controller
```

The physical wire itself is not necessarily directional.

The current prototype's connection-start logic treats the dragged-from port as a source. This should be revisited after basic connection deletion is working.

The likely V0.1-compatible improvement is:

* allow starting a physical connection from either endpoint
* evaluate the pair of ports regardless of which endpoint the user chose first
* retain port direction as semantic information
* do not encode physical wire direction merely from mouse gesture direction

The exact implementation should be decided after observing the simplified prototype.

---

# 9. Compatibility Refinement

Do not significantly expand compatibility rules during the initial refactor.

Current prototype compatibility is intentionally based mainly on:

* port type
* direction

Later refinement should allow semantic distinctions such as:

```text
temperature_measurement
step_command
heater_control
power
ground
communication
```

This is a future semantic layer, not a reason to complicate the initial V0.1 prototype.

# 14. Plan Change Rule

When implementation reveals that the plan is wrong:

Do not force the implementation to match the original plan.

Instead:

1. Record the change.
2. Record why it changed.
3. Update the implementation plan.
4. Update the roadmap only when the decision affects future versions.
5. Continue from the new understanding.

The final version record should explain both what was planned and what was actually built.
