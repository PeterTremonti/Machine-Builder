# 1. Initial Plan

V0.1 establishes the working visual-editor foundation for Machine Builder.

The version was intentionally limited.

The primary goal was to prove that the editor could represent, manipulate, and visually connect machine structures while maintaining clear separation between:

- visual presentation
- visual model data
- mutations
- compatibility logic
- application/editor behavior

The initial implementation plan was to:

1. Preserve the working prototype behavior.
2. Refactor the oversized `canvas.py`.
3. Establish reusable graphics modules.
4. Add persistent port identification and connection feedback.
5. Add direct connection selection and deletion.
6. Establish the correct distinction between physical connections and signal direction.
7. Test the resulting editor interactively and with automated tests.
8. Document lessons learned for the next version.

4. Port Presentation

Persistent port labels were restored after the graphics refactor.

The labels remain visible rather than requiring hover discovery.

Labels may appear outside node boundaries when that produces a more readable presentation.

This was deliberately preferred over forcing labels inside small or crowded component boxes.

Connection-state feedback uses both color and non-color symbols.

Status symbols
✓  compatible
?  unknown or conditional
×  incompatible

Color remains useful, but the state does not depend solely on color.

This supports better readability under conditions such as poor lighting or reduced color discrimination.

5. Connection Model Decision

One of the most important V0.1 architectural decisions was made during interactive testing.

A physical connection is not inherently directional.

The editor therefore distinguishes between:

Physical connection
Endpoint A ↔ Endpoint B

and:

Semantic signal relationship
Source → Consumer

The visual connection model now stores:

endpoint_a_id
endpoint_b_id

rather than:

source_port_id
target_port_id

The ordering of physical endpoints does not imply physical direction.

Port direction and compatibility logic may still determine a meaningful semantic relationship when one exists.

6. Bidirectional Connection Initiation

Because physical connections are not directional, the user can begin creating a valid connection from either endpoint.

For example:

Temperature Output → Temperature Input

and:

Temperature Input → Temperature Output

both create the same physical connection.

The editor checks the semantic compatibility in either orientation.

The stored physical relationship remains:

Temperature Output ↔ Temperature Input

This prevents mouse gesture direction from incorrectly becoming machine-topology information.

7. Compatibility System

V0.1 uses a deliberately provisional compatibility engine.

It distinguishes:

compatible
incompatible
unknown
conditional

The current compatibility rules are intentionally simple.

They primarily use:

port type
port direction

The compatibility engine does not yet model complete semantic signal identities.

For example, multiple different signal-producing ports may currently be considered compatible with a generic signal input even when their eventual machine semantics would make that relationship invalid.

This limitation is intentional and is carried forward as V0.2 work.

Unknown information is not silently treated as confirmed compatibility.

8. Connection Editing

   ↓

   ↓

Connections may be selected:

through normal scene selection behavior

Direct wire selection can be somewhat easier at higher zoom levels, particularly when using a trackpad. This is acceptable for V0.1.

The editor also prevents duplicate physical connections between the same two endpoints.

Repeatedly attempting the same connection produces feedback rather than creating a duplicate edge.

9. Undo / Redo

Undo and redo operate at the level of meaningful user actions.

V0.1 uses model snapshots for reliable history behavior.

Important atomic operations include:

multi-node movement
multi-node deletion
connection creation
connection deletion

This avoids the earlier prototype behavior where large user actions could be undone one small object at a time.

11. Important V0.1 Lessons

Several implementation decisions emerged from real use of the prototype.

Persistent port labels were preferable

Forcing users to hover over ports to discover their identity slowed connection work unnecessarily.

Persistent labels were easier to use and can still be adapted later to different information/detail layers.

Status information should not depend on the status bar

The status bar is useful secondary feedback, but important information should also be visible near the object or interaction that produced it.

This was demonstrated by the fact that the user often focused on the ports and connection colors rather than the status bar.

Small modules are easier to debug

The graphics refactor exposed missing imports and other localized problems quickly.

Moving visual classes into dedicated modules made those failures much easier to isolate than when all graphics code lived in one very large file.

Physical topology and semantic direction must remain distinct

This was the most important architectural correction discovered during V0.1.

A physical wire is a relationship between two endpoints.

The direction of a signal carried through that relationship is separate semantic information.

14. V0.2 Should Not Be Implemented Yet

The existence of the carry-forward list does not automatically authorize implementation.

Before coding V0.2:

Review V0.1 results.
Update the implementation roadmap.
Define V0.2 objectives.
Identify required architecture changes.
Decide which V0.1 discoveries should become formal requirements.
Create a new V0.2 implementation plan.

The next version should start from the completed V0.1 state, not from unfinished V0.1 ideas.
