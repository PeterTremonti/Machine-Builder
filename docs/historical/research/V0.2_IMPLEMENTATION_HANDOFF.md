# Architectural boundary

```text
             Canonical Machine Model
                     ↕
           Semantic / Model Boundary
                     ↕
              Visual Machine Editor
```

The canonical model is the semantic authority.

The visual model is presentation/editing state.

The visual editor is bidirectional:

```text
Canonical → visual projection

Visual user action
        ↓
Semantic mutation
        ↓
Canonical model
        ↓
updated visual state
```

The visual model is not a second canonical machine model.

# What the important implementation files do

## `semantic_model.py`

Canonical semantic model.

Current entities include:

* `Machine`
* `MachineComponent`
* `HardwareDefinition`
* `SemanticPort`
* `Provenance`
* canonical connection storage

The canonical model is independent of visual presentation.

---

## `semantic_connection.py`

Defines the semantic physical connection object.

A canonical connection stores:

* identity
* endpoint port identities
* connection type
* properties
* provenance

Physical connection identity is intentionally distinct from future directional semantic relationships.

---

## `semantic_projection.py`

Projects canonical semantic information into visual presentation.

Canonical meaning drives visual presentation.

Examples:

* port purpose
* port direction
* presentation port type
* semantic references

Visual placement remains presentation state.

---

## `model_boundary.py`

Defines the relationship between canonical and visual models.

The boundary should remain explicit rather than allowing visual objects to become the canonical machine representation.

---

## `editor_state.py`

Holds the combined editor state:

```text
visual_model
semantic_model
```

This is the unit used by the store for state changes and snapshots.

---

## `mutations.py`

Contains executable semantic/visual mutations.

Current important operations include:

```text
CreateNode
CreateMachineComponent
MoveNodes
DeleteNodes
CreateConnection
DeleteConnection
```

Mutations operate on `EditorState`.

The store provides atomic commit/rollback behavior.

---

## `store.py`

Owns editor state and undo/redo.

Current behavior includes:

* commit
* undo
* redo
* rollback after failed mutation
* listeners
* visual-model compatibility access
* canonical-model access

Undo/redo preserves state/value, not Python object identity.

# Current real hardware fixture

The first concrete hardware definition is a generic / unbranded 4010 axial fan.

Important conceptual distinction:

```text
Hardware Definition
generic-4010-fan-24v
```

may be reused by multiple machine components.

But instantiated canonical ports belong to the individual Machine Component.

Example:

```text
Machine Component A
component-fan-a
├── component-fan-a-power
└── component-fan-a-ground

Machine Component B
component-fan-b
├── component-fan-b-power
└── component-fan-b-ground
```

Do not revert these port identities to the hardware-definition port IDs.

This distinction was validated by the two-fan connection tests.

# Current connection behavior

Connections now exist in both layers.

```text
VisualConnection
        ↕
connection ID
        ↕
SemanticConnection
```

When both visual endpoints reference canonical ports:

```text
visual port
    ↓
semantic_reference
    ↓
canonical port
```

creating a visual connection also creates the canonical connection.

Deleting the connection removes both representations.

Undo/redo restores/removes both representations.

Visual-only connections remain supported for compatibility with visual objects that do not yet have canonical semantic references.

# Current architecture rules to preserve

## Canonical model is authoritative

Do not make the visual model the semantic source of truth.

## Component is not hardware definition

A Machine Component is an occurrence in a machine.

A Hardware Definition describes the hardware.

## Component ports have instance identity

A hardware definition can be reused.

Its instantiated machine-component ports cannot share the same canonical identity.

## Physical connection is not necessarily a directional semantic relationship

A physical connection is fundamentally:

```text
Port A ↔ Port B
```

Future semantic relationships may carry direction.

## Unknown information is valid

Do not invent missing information merely to complete a UI.

## Visual routing is presentation

A visual route is not the canonical connection itself.

## Future ideas are candidates

Do not silently enlarge V0.2 whenever an interesting future capability appears.
