# Machine Builder R0.1 → v0.2 Implementation Handoff

## 1. Purpose

This document provides the implementation-facing handoff from the R0.1 research/architecture baseline into the current visual-builder development represented by implementation v0.2.

The purpose is to give the implementation work a concise semantic baseline without requiring the implementation conversation to reconstruct the entire research history.

This handoff does not freeze the full ontology.

It identifies the architectural conclusions that should influence the current implementation and the concepts that should remain intentionally deferred.

4. Current v0.2 Objective

The immediate goal is to establish a reliable implementation pattern for:

Component
    ↓
Port
    ↓
Connection
    ↓
Compatibility
    ↓
Visual Feedback

The first implementation is intentionally small.

It does not attempt to implement the entire long-term ontology.

The purpose is to prove that the visual builder can be built around semantic machine relationships instead of around visual drawing primitives.

5. Primary Architectural Rules for v0.2

The implementation should preserve the following rules.

Rule 1 — Canonical Semantics Are Separate from Visual State

A visual node is not the canonical machine component.

Visual state may include:

position;
size;
selection;
routing;
visibility;
interaction state.

The canonical meaning belongs elsewhere.

Rule 2 — Ports Are First-Class

A component should expose explicit ports.

The user should connect:

Port A → Port B

rather than treating an entire node as the connection endpoint.

Rule 3 — Connection Is Semantic

A connection is a semantic relationship.

The rendered line is a visual representation of that relationship.

Semantic:
    Connection

Visual:
    Line

These must not become the same internal concept.

Rule 4 — Compatibility Is Semantic

Compatibility is determined by properties of the endpoints and applicable rules.

Visual color is only the presentation of the result.

Port Semantics
      ↓
Compatibility Evaluation
      ↓
Connection State
      ↓
Visual Appearance
Rule 5 — Unknown Is Valid

The implementation must not assume that every future property is already known.

Where the current implementation does not know something, it is preferable to represent:

Unknown

rather than inventing a value.

Rule 6 — Firmware Independence

The visual builder must not encode RepRapFirmware, Klipper, Marlin, or another firmware as the canonical machine architecture.

Firmware mappings belong later.

6. Initial Port Test Case

The first deliberately simple connection test may use:

Temperature Sensor
    └── Temperature Output

and:

Temperature Controller
    └── Temperature Input

The intended result is:

Temperature Output
        ↓
Temperature Input

Compatibility:
    Valid

This is an intentionally abstract semantic signal example.

It is not intended to establish a complete thermistor model.

Its purpose is to test the implementation architecture for:

ports;
endpoint selection;
connection creation;
compatibility;
connection state;
visual feedback.
7. Minimum Semantic Port Model

The initial implementation may keep the port model small.

A port should be capable of identifying at least:

Port ID
Owner Component
Port Name
Port Domain / Type
Direction or semantic role
Compatibility information

Not every long-term property needs to be implemented in v0.2.

The model should, however, avoid structures that would make later expansion difficult.

8. Initial Compatibility Model

The first compatibility engine can be intentionally small.

For example:

Temperature Output
    compatible with
Temperature Input

The architecture should leave room for later compatibility properties such as:

Domain
Direction
Voltage
Current
Protocol
Signal Type
Mechanical Interface
Material Type
Other Constraints

The current implementation should not attempt to solve all of these at once.

9. Connection Lifecycle

The intended user interaction is approximately:

1. User begins interaction on Port A.
2. User drags toward Port B.
3. A connection preview appears.
4. Compatibility is evaluated.
5. User releases on Port B.
6. Semantic Connection is created if permitted.
7. Visual representation updates.
8. Undo/redo can reverse the model mutation.

The exact UI behavior may differ.

The semantic sequence should remain consistent.

10. Connection Preview

A temporary drag preview is UI state.

It is not a permanent semantic Connection.

Conceptually:

User Drag
    ↓
Temporary Preview
    ↓
Compatibility Evaluation
    ↓
Accepted
    ↓
Semantic Connection

Canceling a drag should not create a permanent connection.

11. Invalid Connection Behavior

When a proposed connection is incompatible, the implementation should distinguish:

Preview:
    incompatible

Final model:
    no semantic connection

The UI may still display the proposed endpoint interaction for feedback.

The semantic model should not contain an invalid permanent connection unless the architecture explicitly supports unresolved connections later.

12. Unknown Compatibility

The compatibility system should eventually support:

Compatible
Incompatible
Conditional
Unknown

For v0.2, a smaller implementation may initially support only:

Compatible
Incompatible

provided the internal design does not prevent adding:

Unknown
Conditional

later.

13. Visual Connection State

The visual builder may communicate semantic state through:

color;
line style;
endpoint highlighting;
preview state;
warnings.

However:

The visual state must be derived from the semantic state.

Do not make color itself the stored semantic truth.

14. Undo / Redo

A semantic connection is a model mutation.

Therefore:

Create Connection
Delete Connection
Change Connection Property

should eventually be represented as undoable semantic operations.

Undo should reverse the model mutation rather than merely deleting or recreating drawing objects.

15. Deletion

Deleting a visual representation should not be treated as automatically equivalent to deleting a canonical machine object.

For example:

Delete Visual Node

could eventually mean:

remove the visual representation;
hide the object;
delete the canonical object.

Those are different operations.

For v0.2, implementation may remain simpler, but the distinction must not be architecturally lost.

16. Selection

Selection is visual/application state.

A selected component or port is not semantically different merely because it is selected.

Selection should therefore remain outside the canonical machine meaning.

17. Position

Node position is visual state.

It must not be interpreted as:

Physical Location

The distinction is:

Visual Position
    ≠
Machine Position

This becomes increasingly important when physical machine coordinates and CoordinateFrames are implemented.

18. Current Visual Model Boundary

The current implementation should conceptually maintain:

Canonical / Semantic Data
        │
        ▼
Visual Projection
        │
        ▼
Qt / Canvas Rendering

The exact internal implementation may simplify this while the project is small.

The long-term direction should remain clear.

19. Current Component Model

The current visual builder may use simplified component definitions.

A visual test component can contain:

Component ID
Display Name
Component Type
Ports
Visual Properties

The implementation does not yet need the complete Machine Component ontology.

However, future expansion should allow a visual component to reference a richer canonical entity.

20. Relationship to Machine Component

The current visual "component" should not be assumed to be the final Machine Component concept.

Eventually the structure may become:

Canonical Machine Component
        ↓
Visual Representation

The current implementation can use a simplified object until the canonical model is mature enough to connect directly.

21. Important Ontology Constraints

The current implementation must remain compatible with these established distinctions:

Axis ≠ Motor
Axis ≠ Joint
Joint ≠ Actuator
Motor ≠ Drive
Drive ≠ Controller

Sensor ≠ Measurement Result
Measurement Result ≠ Feedback

Tool ≠ Toolhead
Toolhead ≠ Carriage

Port ≠ Connector
Port ≠ Pin

Connection ≠ Visual Line

Physical Connection ≠ Logical Mapping

Configuration ≠ Runtime State

Firmware Term ≠ Canonical Concept

These distinctions should not be collapsed merely to make an early UI implementation simpler.

A simplified future structure might include:

subsystem containment;

The Promega should eventually be used as a more realistic canonical-machine test.

Potential elements include:

Machine

├── Motors

25. Firmware Boundary for v0.2

No firmware-specific configuration generation is required for the current connection milestone.

The implementation should not introduce unnecessary firmware concepts simply because future firmware translation exists.

The correct sequence is:

Visual / Semantic Model
        ↓
Canonical Machine Model
        ↓
Future Firmware Mapping

not:

Visual Node
        ↓
Firmware Setting
26. Provenance Boundary for v0.2

Full provenance is not required for the current visual connection milestone.

However, future model structures must remain capable of recording:

Source
Method
Date
Confidence
Evidence

for important facts and relationships.

Do not design the initial implementation in a way that permanently assumes every value has no origin.

30. Research Feedback Expected from v0.2

Implementation should report back if any of these occur:

Finding A

A port needs information not currently represented.

Finding B

Connection compatibility cannot be determined from the current port model.

Finding C

The distinction between visual and canonical data is difficult to maintain.

Finding D

Undo/redo requires semantic operations not yet defined.

Finding E

Multiple connection types reveal that "Connection" needs domain-specific structure.

Finding F

Subsystems or grouped components expose missing relationship types.

These are research findings, not merely implementation bugs.

31. Implementation Success Criteria

The current handoff is successful when v0.2 demonstrates that:

1. Components can expose semantic ports.
2. Ports can participate in semantic connections.
3. Compatibility can be evaluated independently of drawing.
4. Visual feedback can be derived from semantic state.
5. Connections can be created and removed reliably.
6. Undo/redo can operate on semantic mutations.
7. The architecture remains capable of supporting richer canonical concepts later.
32. Known Deliberate Simplifications

The following simplifications are acceptable for v0.2:

Simple component types
Simple port types
Simple compatibility rules
Limited provenance
Limited property model
Limited persistence
No complete firmware mapping
No complete machine ontology
No advanced kinematics

These are implementation-stage simplifications, not architectural decisions to remove the corresponding future concepts.

33. Current Handoff Principle

The current implementation should follow:

Small Semantic Core
        ↓
Working Visual Behavior
        ↓
Automated Tests
        ↓
Real Machine Stress Case
        ↓
Generalization

This is preferable to implementing the entire ontology before proving that the core interaction architecture works.

34. Final Handoff Rule

The purpose of this handoff is not to make v0.2 implement all of R0.1.

It is to make sure the current implementation does not accidentally violate the architectural conclusions that R0.1 established.

The implementation should therefore be:

Simple enough to build now
        +
General enough to grow later
        +
Explicit enough to test
        +
Semantically aligned with the research

When implementation evidence reveals a limitation, return that evidence to the research/ontology work rather than hiding the limitation in an implementation-specific workaround.
