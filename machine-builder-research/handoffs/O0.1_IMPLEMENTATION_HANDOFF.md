# O0.1 Implementation Handoff

## Purpose

This handoff tells implementation work what the O0.1 research checkpoint now guarantees and what it deliberately does not guarantee.

## Canonical machine principle

The canonical machine model is the source of machine meaning and the authoritative structured representation of the machine.

```text
Physical / canonical model
        ↓
Firmware requirements
        ↓
Target firmware mapping
        ↓
Generated representation
```

Reverse:

```text
Firmware/configuration
        ↓
Semantic parsing
        ↓
Canonical model
```

The visual editor is a bidirectional authoring and inspection environment for the canonical model.

```text
            Canonical Machine Model
                    ↕
          Semantic / Model Boundary
                    ↕
             Visual Machine Editor
```

## Minimum implementation domains

Implement enough data and behavior to represent:

- Machine
- Machine Component
- Subsystem
- Axis
- Motor / Actuator / Drive
- Extruder / Tool
- Heater / Fan
- Sensor / Probe / Endstop
- Controller
- Controller Resource
- Electrical Port
- Connector
- Pin/terminal
- Electrical Connection
- Function / Capability
- Property
- Calibration
- Provenance
- Firmware context

## Visual editor relationship

The visual editor must be understood as an authoring and inspection interface over canonical machine semantics, not as a read-only consumer.

The editor must support both:

```text
Canonical Machine Model
        ↓
Visual projection
        ↓
Editor
```

and:

```text
User action
     ↓
Semantic edit / mutation
     ↓
Canonical Machine Model
     ↓
Updated visual representation
```

The editor may author and modify canonical entities and relationships including, as applicable:

- Machine Components
- Subsystems
- Ports
- Connectors / pins / terminals
- Connections
- Functions
- Capabilities
- Controller-resource assignments
- Properties
- Calibration information
- other canonical relationships

A visual connection is a rendering/editing representation of a semantic connection.

Do not make canvas geometry the source of machine topology.

Do not allow the visual layer to become an independent semantic machine model.

## Viewing and Editing

**Viewing mode** is primarily for inspection, navigation, filtering, and relationship exploration.

**Editing mode** is for authoring and changing canonical machine semantics and relationships.

Both modes operate on the canonical machine model.

## Connection engine test

The existing Controller → Motor connection test is appropriate.

Future compatibility evaluation can use semantic properties including, where applicable:

- connection domain
- direction
- voltage
- current
- protocol
- interface type
- pin/terminal compatibility
- controller-resource availability

These values should come from canonical component/interface/resource semantics, not hard-coded visual colors.

## Firmware handoff

Firmware-specific commands and configuration keys should not be stored as the meaning of the machine.

The implementation will eventually need a separate firmware knowledge base containing at least:

- firmware family
- firmware version/range
- canonical concept
- firmware term or representation
- mapping type
- prerequisites/constraints
- compatibility information
- source/evidence
- notes/examples

The knowledge base should be locally versioned for reproducible translation. External repositories/documentation can be import/update sources but should not be required for normal deterministic generation.

## Critical implementation distinction

These are different:

```text
Machine Component
Hardware Definition
Catalog Product
Controller Resource
Firmware Resource Mapping
Visual Representation
Visual Presentation State
```

A Machine Component is the machine-specific semantic object.

A Hardware Definition describes the hardware identity/specification associated with that Machine Component when known.

A Catalog Product is an external reusable product definition.

A Controller Resource is a resource supplied by a Controller and allocated to machine semantics.

A Firmware Resource Mapping expresses how canonical semantics are represented in a target firmware.

A Visual Representation is how a canonical entity or relationship is shown/edited by the visual editor.

Visual Presentation State is UI state such as position, size, routing, selection, and zoom.

Example:

```text
Physical X motor
    ↓
Canonical Machine Component
    ↓
hardware definition when known
    ↓
canonical allocation
    ↓
Controller driver resource
    ↓
Firmware-specific stepper representation
    ↓
Visual representation
```

## Partially specified machines

The implementation must allow:

```text
known machine semantics
    +
unknown hardware identity
    +
unknown properties/specifications
```

without inventing placeholder values.

Unknown is a valid modeled state and must remain distinct from:

- absent
- not applicable
- zero
- empty string
- default value
- guessed hardware

Example:

```text
Temperature Sensor component exists
intended role = known
placement = known
connections = known
hardware definition = unspecified
electrical specifications = unknown
```

This is a valid partially specified machine.

## Replace Component

Replace Component is an intended semantic editing operation.

The purpose is to replace or enrich the hardware definition associated with an existing Machine Component while preserving the machine-specific object and its existing semantic relationships unless the user explicitly changes them.

Do not normally implement Replace Component as:

```text
delete old Machine Component
create new Machine Component
```

Instead:

```text
existing Machine Component
        ↓
preserve identity and relationships
        ↓
replace / enrich hardware definition
        ↓
updated Machine Component
```

Existing role, placement, connections, subsystem membership, relevant ports/interfaces, Functions, and other machine-specific relationships should remain unless explicitly modified.

The exact implementation mechanism is deferred, but delete/recreate semantics are explicitly undesirable because they can destroy identity, relationships, connections, placement, role, and provenance.

## Provenance

User-authored semantic information must be capable of carrying provenance such as:

```text
source: user
evidence type: authored
method: visual editor
context: editor session
```

This must not be confused with externally verified manufacturer information or other evidence types.

## Calibration

The model must permit:

```text
nominal/derived value
calibrated/working value
```

to coexist. A discrepancy may trigger a calibration note/warning instead of being silently overwritten.

## Unknown / absent / unspecified / not applicable

Do not confuse:

- absent — the machine does not have the thing;
- unknown — the information exists in principle but has not been established;
- unspecified — intentionally left open at the current authoring stage;
- not applicable — the concept does not apply.

For hardware identification, an intentionally unspecified Hardware Definition is valid.

A printer without a heated bed should not receive a fake Heat Bed component just because another printer has one.

## Future change review

The architecture should eventually permit editor operations to produce a semantic change set before commit.

Example:

```text
Added Temperature Sensor
Connected Sensor → Controller
Assigned role: temperature measurement
Hardware definition: unspecified
```

The user may eventually review and confirm the proposed changes before they become committed canonical model state.

This is a future architectural direction, not an immediate V0.2 implementation requirement.

## Current visual implementation should not be blocked

The connection engine can continue being implemented and tested before all canonical-machine editing features exist.

The existing V0.1 connection prototype remains useful as a proof of interaction/presentation mechanics and canonical Port/Connection projection. It should not be expanded into a separate long-term semantic connection model.

Research questions that are not needed by the current connection test should not be allowed to block it.

## O0.2 targets

Do not implement these as O0.1 requirements:

- water-cooling/plumbing model
- general fluid systems
- hydraulic/fuel systems
- generalized material plumbing
- broad process/operation ontology

Those are deliberate follow-on expansions.
