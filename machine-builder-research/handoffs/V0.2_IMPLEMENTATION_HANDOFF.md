# V0.2 Implementation Handoff

## Purpose

This is the implementation-facing handoff from the completed V0.2 research checkpoint.

V0.2 is based on the O0.1 canonical machine model.

The primary goal remains:

> Build, describe, inspect, and semantically author real 3D-printer machines, with enough canonical information to support firmware-oriented work.

The visual editor is the primary implementation surface.

---

## 1. Architectural boundary

```text
Canonical Machine Model
        ↕
Semantic / Model Boundary
        ↕
Visual Machine Editor
```

The editor is both:

```text
projection / inspection
```

and:

```text
semantic authoring / editing
```

It is not a second machine model.

---

## 2. V0.2 semantic editing

The editor should be able to author/modify canonical information including, as applicable:

```text
Machine Components
Subsystems
Ports
Connectors
Pins / Terminals
Connections
Functions
Capabilities
Controller-resource assignments
Properties
Calibration
canonical relationships
```

Existing visual geometry must remain separate from semantic identity.

---

## 3. View mode

View mode must not mutate canonical state.

View-only controls may include:

```text
geometric zoom
semantic zoom
detail level
filters
layers
selection
relationship exploration
capability/function exploration
domain-specific views
```

The same canonical machine is being viewed regardless of the selected presentation.

---

## 4. Edit mode

Edit mode may change canonical semantics.

For V0.2, semantic edits should eventually include:

```text
add component
remove component
replace/enrich hardware definition
edit role
edit properties
create connection
edit connection
assign controller resource
create/edit Function
create/edit Capability
edit calibration information
```

The future change-review/confirmation workflow is architectural direction but not required to finish the first V0.2 editor.

---

## 5. Partial specification

The editor must support:

```text
known semantic role
+
unknown/unspecified hardware identity
+
unknown specifications
```

Do not create fake catalog products or placeholder values to make a UI complete.

Preserve distinctions among:

```text
absent
unknown
unspecified
not applicable
known
measured
derived
inferred
configured
calibrated
```

---

## 6. Relationship implementation

The editor and model boundary should be prepared for typed semantic relationships.

The minimum useful relationship distinctions identified by research are:

```text
structural
interface/topology
functional
dependency
allocation/configuration
```

Examples:

```text
attached_to
connected_to
terminates_at
participates_in
realizes
supports
requires
depends_on
prerequisite_for
assigned_to
controlled_by
mapped_to
```

Do not implement all possible future relationship types simply because they appear in the research notes.

Preserve the semantic distinction even if the initial implementation supports only a subset.

---

## 7. Direction

Connections/relationships should support direction only when direction is semantically meaningful.

Examples:

```text
Sensor → Controller
Controller → Driver
Pump outlet → Hotend inlet
Hotend outlet → Radiator
```

Physical wire geometry should remain separate from semantic direction.

The future visual system may animate directed signals/flows, but the animation is not canonical machine data.

---

## 8. Ports / connectors / pins

V0.2 should continue toward progressive detail:

```text
Component
    ↓
Port / Interface
    ↓
Connector
    ↓
Pin / Terminal
    ↓
Connection / signal / conductor detail
```

Do not require all levels to be populated for a partially specified machine.

The canonical machine may stop at the level actually known.

---

## 9. Visual detail

Treat these as separate presentation concepts:

```text
Geometric Zoom
Semantic Zoom
Detail Level
```

User-facing detail levels are intended to become:

```text
Beginner
Intermediate
Expert
```

Canonical information is not removed at lower detail levels.

The UI simply reveals less of it.

---

## 10. Layers and filtering

Filtering/layering is view state.

Useful future scopes include:

```text
Motion
Electrical
Thermal
Fluid
Sensors
Controllers
Functions
Capabilities
selected components
```

The same object may appear in multiple views.

Filtering must never reassign the machine or change canonical semantics.

---

## 11. Visual routing

Orthogonal routing is recommended:

```text
horizontal
vertical
90-degree turns
avoid crossing/hidden routes where practical
```

A visual route is not the canonical Connection.

Grid/snap/alignment can be implemented as UI assistance.

---

## 12. Purpose icons

Purpose-based icons are presentation.

Examples:

```text
Fan → fan icon
Heater → flame
Temperature sensor → thermometer
Motor → motion/rotation symbol
Power → power/lightning symbol
Endstop → switch
```

Icons must not become the semantic source of meaning.

The canonical classification/function data supplies meaning to the presentation layer.

---

## 13. Liquid cooling

V0.2 may experiment with a minimum liquid-cooled hotend representation:

```text
coolant
cooling block
coolant inlet/outlet
tubing
fittings
pump
optional reservoir
radiator / heat exchanger
radiator fan
optional coolant temperature sensor
optional fill/drain interfaces
```

Fluid direction should be represented.

This is a controlled expansion for V0.2 implementation/research and should not silently redefine O0.1 into a universal fluid ontology.

---

## 14. What V0.2 should NOT become

Do not turn V0.2 into:

```text
a slicer
a printer-host replacement
Fluidd
Mainsail
OrcaSlicer
a live telemetry dashboard
a printer-control application
a simulation engine
a diagnostic engine
a safety system
a universal engineering ontology
```

Those are future integrations/directions.

The V0.2 Machine Builder is primarily the machine architecture/modeling and firmware-oriented authoring environment.

---

## 15. Firmware boundary

Firmware remains an implementation context.

Use:

```text
canonical machine semantics
        ↓
firmware requirements/mapping
        ↓
firmware representation
```

Do not make firmware-specific terms the canonical meaning.

The same canonical machine should eventually be able to map toward supported firmware families/versions.

---

## 16. Implementation priority

The recommended implementation priority is:

```text
1. Canonical model boundary
2. Machine Component authoring
3. Ports / Connections
4. Function / Capability authoring
5. Controller resources / allocations
6. Properties / provenance / partial specification
7. Visual projection
8. Semantic editing
9. View/Edit separation
10. Semantic zoom / detail levels
11. Filters/layers
12. Orthogonal routing/grid/snap
13. Minimum liquid-cooling representation
```

The exact order may be adjusted when implementation evidence requires it, but semantic requirements should not be silently changed merely for implementation convenience.

---

## 17. Success criterion

V0.2 is complete when the editor can construct and inspect a meaningful 3D-printer machine from canonical semantics rather than merely drawing disconnected boxes and lines.

A useful test machine should be complex enough to exercise:

```text
Motion
Extrusion
Thermal control
Sensors
Controller resources
Electrical connections
Functions
Capabilities
Partial specification
Provenance
```

A liquid-cooled hotend should be usable as the first non-electrical physical-interface stress case.

---

## 18. Future integration direction

Future Machine Builder versions may integrate with external printer/slicer ecosystems rather than reimplementing those systems.

Promising future integrations include:

```text
OrcaSlicer
Cura
printer hosts / APIs
Moonraker
Fluidd/Mainsail ecosystem
RepRapFirmware interfaces
other supported printer-host mechanisms
resin-printer slicers
```

These are future integration targets.

They are not dependencies of the V0.2 canonical machine editor.
