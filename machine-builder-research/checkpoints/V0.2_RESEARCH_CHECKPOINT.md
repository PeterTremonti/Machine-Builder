# Machine Builder V0.2 Research Checkpoint

## Status

This checkpoint defines the research/architecture stopping point for V0.2 implementation.

The project remains grounded in the O0.1 canonical machine model.

```text
R0.1 Research / Architecture
        ↓
O0.1 Canonical semantic foundation
        ↓
V0.2 Implementation
```

V0.2 is not a new universal ontology.

It is the first implementation milestone in which the visual editor begins operating as a real bidirectional authoring and inspection environment for the canonical machine model.

The original project purpose remains primary:

> Build and describe a physical 3D printer, understand how its parts and relationships work together, derive firmware requirements/mappings, and eventually assist with generating or translating firmware representations.

Future monitoring, simulation, diagnostics, printer control, slicer integration, and safety systems remain future directions and are not V0.2 requirements.

## 2. Function and Capability boundary

### Capability

A Capability is an ability or outcome the machine or subsystem can provide.

Examples:

```text
Move X
Maintain hotend temperature
Extrude material
Automatically tram gantry
Compensate for bed-surface variation
```

A Capability may depend on multiple Functions, machine components, controller resources, relationships, configuration, and applicable constraints.

Capability is not simply a Boolean property of a component.

A machine may retain some capabilities while losing others when a component, resource, relationship, or configuration is removed.

### Function

A Function is an identifiable machine behavior/service.

Examples:

```text
Move X
Establish Z reference
Measure hotend temperature
Control hotend temperature
Extrude filament
Detect filament movement
Adjust independent Z positions
```

A Function:

* can have semantic identity;
* can involve multiple machine objects/resources;
* can participate in relationships with other Functions;
* is not a physical Machine Component;
* is not a universal parent of Task, Process, Operation, Action, or Procedure.

A Function may be decomposed or realized by multiple machine elements without those elements becoming the Function itself.

### Deferred execution vocabulary

The following remain intentionally outside the V0.2 core semantic model:

```text
Task
Process
Operation
Action
Procedure
```

Research establishes that these concepts are meaningful and distinct from Function, but V0.2 does not require a complete execution/process ontology.

## 3. Relationship requirements

The stress-testing phase did not reveal a missing fundamental entity.

Instead, it repeatedly demonstrated that relationships need to preserve semantic differences.

V0.2 therefore requires typed semantic relationships rather than a generic "related to" relationship.

The minimum useful relationship families are:

```text
Structural
    contains
    member_of
    attached_to / mounted_to where applicable

Interface / topology
    connected_to
    terminates_at
    carries / transports where applicable

Functional
    participates_in
    realizes
    supports

Dependency
    requires
    depends_on
    prerequisite_for

Allocation / configuration
    assigned_to
    controlled_by
    mapped_to
```

The exact implementation names may differ, but the semantic distinctions must remain expressible.

Not every relationship is directional.

Where direction is semantically meaningful, it must be represented separately from physical geometry.

Examples:

```text
Sensor → Controller
Controller → Heater
Pump Outlet → Coolant Inlet
Coolant Outlet → Radiator
```

A physical wire/path is not automatically a directional signal merely because the signal carried by it is directional.

A visual line is never the canonical relationship itself.

---

## 4. Physical topology versus functional semantics

The model must distinguish:

```text
physical connection
physical attachment
electrical/interface topology
functional participation
functional realization
resource allocation
firmware mapping
```

A component being physically connected to another object does not automatically mean that it participates in the same Function.

Conversely, a Function may be realized by multiple physically separate components and resources.

Examples:

```text
Fan
    attached_to → bracket

Fan
    participates_in → Cool Printed Material
```

and:

```text
Maintain Hotend Temperature
    realized through:
        heater
        temperature sensor
        controller resource
        hotend
        cooling system
```

These are different semantic relationships.

---

## 5. Controller Resource principle

Controller Resources remain distinct from both physical Machine Components and Functions.

A resource may be:

```text
Stepper driver
GPIO
ADC
PWM output
Timer
UART
CAN
Ethernet
```

Hardware documentation is authoritative for the physical capabilities and limits of the underlying controller hardware/resource when known.

Firmware configuration determines how that resource is mapped and used in the particular machine.

For example:

```text
Hardware:
    PWM-capable 24 V output

Machine wiring:
    connected to two physical fans

Firmware:
    assigned as part-cooling output

Machine semantics:
    supports part-cooling Function
```

A resource described by firmware as a "fan output" is not thereby ontologically a Fan resource.

A compatible PWM output may technically control different loads when the hardware electrical limits permit it. The Machine Builder should represent the actual hardware capability, actual connection, and actual firmware/machine role separately.


The editor must never invent values merely to satisfy implementation convenience.

## 7. Canonical model versus presentation

The canonical model is the authoritative machine representation.

Presentation state is separate.

Presentation state may include:

```text
canvas position
node size
routing
selection
geometric zoom
semantic zoom
detail level
collapsed/expanded state
filter state
layer visibility
grid visibility
snap settings
other UI-only state
```

These do not alter the machine merely because the user changes them.

## 8. View and Edit modes

### View mode

View mode is observational.

It may provide:

```text
inspection
navigation
relationship exploration
semantic zoom
detail levels
filtering
layers
capability/function exploration
electrical or other domain views
```

Changing any of these does not modify canonical machine state.

### Edit mode

Edit mode allows:

```text
creating canonical entities
modifying canonical entities
creating relationships
modifying relationships
assigning resources
editing properties
editing calibration information
editing other canonical information
```

Complex future edits should eventually support review/change-set confirmation before commit, but this is not a V0.2 implementation requirement.

---

## 9. Visual detail and zoom

Three presentation concepts should remain conceptually separate:

```text
Geometric Zoom
    How much physical/canvas space is visible.

Semantic Zoom
    How much semantic detail about visible entities/relationships is exposed.

Detail Level
    How much explanation/information is presented to the user.
```

The intended user-facing detail levels are:

```text
Beginner
Intermediate
Expert
```

The canonical model does not become less detailed for a beginner.

The user interface simply exposes less of the available information.

Example:

```text
Beginner:
    X Axis
    Motor
    Carriage

Intermediate:
    X Axis
    Motor
    Drive
    Endstop
    Calibration

Expert:
    Function
    Kinematic relationship
    Controller resource
    Ports
    Connections
    Calibration
    Firmware mapping
    Provenance
```

## 10. Filtering and semantic layers

Filtering and layers are presentation/navigation mechanisms.

Examples include:

```text
Motion
Electrical
Thermal
Fluid
Sensors
Controllers
Functions
Capabilities
Selected components
```

Filters must not change canonical machine state.

A component may appear in multiple semantic views because it can participate in multiple domains/functions.

Filtering means:

> Show relationships/entities relevant to this selected semantic scope.

It does not mean:

> Reassign the component to a different physical or semantic layer.

---

## 11. Visual connection routing

Orthogonal routing is a presentation feature.

The intended visual behavior is:

```text
horizontal
vertical
90° turns
routing around nodes
```

A visual route does not become the canonical Connection.

The canonical Connection stores machine meaning.

The renderer chooses how that meaning is presented.

---

## 12. Grid, snapping, and alignment

The visual editor should move toward a CAD/Blender-like interaction model without attempting to reproduce Blender in full.

Useful visual facilities include:

```text
grid
optional grid snapping
alignment
port/connector snapping
pin snapping
route-point snapping
frame selected
smooth geometric zoom
```

These are presentation/editing aids and do not become canonical machine semantics.

Blender's current viewport/grid/snapping behavior is a reasonable interaction precedent, not a requirement to reproduce its implementation.

---

## 13. Directional visualization

Where canonical semantics contain direction, the visual editor may represent that direction through:

```text
arrows
flow indicators
signal direction
animated flow/pulse effects
```

Examples:

```text
Sensor → Controller
Controller → Heater

Pump Outlet → Hotend Inlet
Hotend Outlet → Radiator
```

Animation is presentation.

The underlying direction is semantic.

## 14. V0.2 liquid-cooled hotend scope

Liquid cooling is the controlled additional domain for V0.2 experimentation.

This is intentionally a **minimum practical representation**, not a universal fluid ontology.

A liquid-cooled hotend may contain:

```text
Coolant
Cooling block / cold plate
Coolant inlet
Coolant outlet
Tubing / plumbing
Fittings / connectors
Pump
Reservoir [optional]
Radiator / heat exchanger
Radiator fan(s)
Coolant temperature sensor [optional]
Fill interface [optional]
Drain interface [optional]
```

Fluid direction must be representable.

Example:

```text
Pump outlet
    ↓
Hotend coolant inlet
    ↓
Cooling block
    ↓
Hotend coolant outlet
    ↓
Radiator
    ↓
Reservoir
    ↓
Pump inlet
```

A reservoir may have a fill interface without having a dedicated drain interface.

A system may be drained through another physical means, but the specific maintenance procedure is outside the V0.2 semantic scope.

### Deliberately deferred liquid-cooling detail

Do not make these V0.2 requirements:

```text
flow-rate semantics
flow sensors
leak detection
coolant-level sensing
pressure
coolant chemistry/properties
general fluid safety ontology
universal plumbing ontology
maintenance procedure ontology
```

These remain future research candidates.

## 15. Printer stress-test conclusions

The semantic stress testing used ordinary and nontrivial printers including:

```text
Cartesian
CoreXY
Multiple-Z
Synchronized dual-Z
Independently controlled multi-Z
Bed mesh systems
Manual bed measurement
Extrusion systems
Filament sensors
Shared controller resources
Thermal systems
Liquid cooling
```

The major conclusion is:

> The existing core entity vocabulary survives these cases. The difficult cases primarily require richer and more precise relationships, not new fundamental classes.

Examples:

```text
one Component → many Functions
many Components → one Function
one Resource → many Components
one Resource → many Functions
Function → prerequisite Function
Function → supporting Function
physical connection ≠ functional relationship
Capability ≠ component identity
Capability ≠ current state
```

## 17. V0.2 success criterion

V0.2 is successful when a user can construct and inspect a meaningful 3D-printer machine model through the visual editor without the editor becoming a separate semantic model.

The resulting machine representation should be capable of describing:

```text
what the machine physically contains
how the machine is connected
what its components/resources are capable of supporting
what Functions and Capabilities are present
how those semantics relate to one another
what is known/unknown/unspecified
where information came from
what firmware context is associated with it
```

The visual editor should make that information understandable at multiple presentation/detail levels without changing the machine merely by viewing it.

---

## 18. Checkpoint stopping rule

This checkpoint is intentionally the stopping point for V0.2 semantic expansion.

Future ideas should be recorded, but should not automatically alter V0.2.

A new semantic requirement should be promoted only when:

```text
real machine evidence
or
firmware evidence
or
implementation evidence
or
research evidence
```

demonstrates that the current model is insufficient.

The next major research checkpoint should reconcile:

```text
research results
+
visual-editor implementation experience
+
actual machine modeling
```

before modifying the durable ontology.
